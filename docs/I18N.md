# Localization (English / Russian)

The console ships two languages and a switcher in the header. This document
describes how it works, why it is built the way it is, and what it costs to add a
third language.

## The one invariant

**A screen renders in the right language on the first paint, with no client-side
state.** The locale is a cookie (`lh_locale`), read on the server by
`getI18n()`. Nothing about the UI is translated in the browser, so there is no
flash of English, no hydration mismatch, and no i18n bundle shipped to the client.

```
cookie lh_locale ──▶ getI18n() ──▶ { locale, t }
                        │
                        └─▶ DICTIONARIES[locale]   (en.ts | ru.ts)
```

## Files

| Path | Role |
| --- | --- |
| `src/i18n/config.ts` | The locale list, the default, the cookie name, display names, the `isLocale` guard |
| `src/i18n/en.ts` | English strings **and the `Dictionary` type** every other language is checked against |
| `src/i18n/ru.ts` | Russian strings, typed as `Dictionary` |
| `src/i18n/index.ts` | Server entry point: reads the cookie (cached per request), returns `{ locale, t }`; re-exports the pure helpers |
| `src/i18n/text.ts` | Pure helpers — `template`, `plural`, `errorText`, `duplicateReasonText`, `eventMessageText`. No `next/headers`, so tests and client components can import them |
| `src/i18n/actions.ts` | The `setLocaleAction` server action that writes the cookie |
| `src/components/language-switcher.tsx` | The segmented EN/RU control — plain form buttons, works without JavaScript |

## How a screen uses it

```tsx
const { locale, t } = await getI18n();

<h1>{t.dashboard.heading}</h1>
<span>{t.enums.temperatures[lead.temperature]}</span>
<span>{relativeAge(lead.createdAt, locale, now)}</span>
```

Three rules cover almost every string:

1. **Copy lives in the dictionary**, never inline in a page.
2. **Enums are looked up, not string-formatted.** `WEBSITE` renders as
   "Website" / "Сайт" through `t.enums.categories`, not by replacing underscores
   with spaces. The same applies to statuses, temperatures, urgencies, source
   kinds, event types, analysis statuses, outreach statuses and the eight scoring
   factors.
3. **Numbers, dates and relative times go through `Intl`**, not the dictionary —
   `formatBudget`, `formatDate` and `relativeAge` in `src/components/ui.tsx` take
   the locale and use `Intl.NumberFormat`, `Intl.DateTimeFormat` and
   `Intl.RelativeTimeFormat`. Currency stays an ISO code (`EUR 2 000`), which needs
   no translation, and Russian gets `2 000` and `10 мин. назад` for free.
4. **Counts pick a plural form by locale.** `plural(locale, n, { one, few, many })`
   implements the Russian rules, so the lead list header reads "1 лид", "2 лида",
   "5 лидов" (and "11 лидов", "21 лид") instead of a two-form approximation.
   English keeps `one` elsewhere and only ever uses `one` / `many`; the `few` key
   still exists in `en.ts`, because the two dictionaries must have identical keys.

## Errors are codes, not sentences

The single most important design decision here. Server actions, the pipeline and
the outreach layer **never** put prose in a redirect URL. They send a stable code:

```
/leads/<id>?warning=budgetExceeded
/new?error=contentTooLong
/leads/new?duplicate=overlapSameAuthor&percent=91
```

The screen renders it through `errorText(t, code, params)`. Consequences:

- the same failure reads correctly in both languages — one code, two sentences;
- a message can never appear half-translated;
- **URLs stay safe.** English prose in a redirect URL once contained a bare `%`
  ("91% text overlap") and crashed the page with `URIError`; codes cannot;
- an unrecognised code degrades to `errors.unknown` rather than leaking a raw
  identifier or an English sentence into the Russian UI.

The accepted codes are derived from the dictionary at runtime
(`Object.keys(en.errors)`), so adding `errors.someNewCase` to both dictionaries is
all it takes to make `?warning=someNewCase` render. `errorText` and
`duplicateReasonText` live in `src/i18n/text.ts` and are covered by
`tests/i18n.test.ts`.

`BudgetExceededError.limit` is injected at render time (`{ limit: 250 }`), which
is why `contentTooLong` and `budgetExceeded` can name a number without the action
knowing the language. The screen supplies the limit it actually enforces
(`MAX_CONTENT_LENGTH`), never a number taken from the URL — `?limit=1` cannot make
the UI advertise a limit the server does not use.

## The switcher

`LanguageSwitcher` is a `<form action={setLocaleAction}>` with one submit button
per locale — no client component, no JavaScript needed, and `aria-pressed` marks
the active one. It appears in the console header **and** on the sign-in screen:
nobody should have to read a foreign language to find the password field.

`setLocaleAction` is deliberately the one action that does not call
`requireOwner()`: it writes a display preference and nothing else. It rejects any
locale outside `LOCALES`, uses a long-lived `SameSite=Lax` cookie that is *not*
`httpOnly` (it is a preference, not a credential) and revalidates the root layout
so every server component re-reads the dictionary.

## What is deliberately not translated

- **AI output** — project descriptions, reasoning, response drafts. The model
  answers in the language of the source post; translating it would invent facts.
- **Stored activity messages** — `lead_events.message` is written once, in English,
  when the event happens. It is a log line, not UI copy. Event *type labels* are
  translated.

The one exception is a **deduplicated sighting**. That row stores today's reason
as a *code* (`metadata.reason = "overlapSameAuthor"` plus `percent`), so
`eventMessageText(t, event)` re-renders it from the same data the banner uses:
"Дублирующий пост пропущен (тот же автор, совпадение текста 91%)". Anything else —
including a row whose metadata is not a code we recognise — falls back to the
stored prose, so an unknown or legacy row degrades instead of disappearing.
Rows written **before** the codes refactor stored the reason as English prose
("same author, 91% text overlap") and therefore still render in English; the
fallback is the reason that is safe rather than a guess at parsing prose.
- **Prompt text** (`src/ai/prompts.ts`) — frozen for prompt caching and asserted
  date-free by `tests/prompts.test.ts`. Localizing it would invalidate the cache on
  every language switch for no benefit.
- **Provider errors** shown in the AI-run list — the vendor's own diagnostic text.

## Adding a third language

1. Add the code to `LOCALES` and its labels to `LOCALE_LABELS` / `LOCALE_NAMES` in
   `src/i18n/config.ts`.
2. Copy `src/i18n/en.ts` to `src/i18n/<code>.ts` and translate the values. The file
   is typed `Dictionary`, so a missing or renamed key fails `npm run typecheck` —
   you cannot ship a half-translated screen by accident. If the language has plural
   rules unlike English's two forms, extend `pluralCategory` in `src/i18n/text.ts`;
   the three keys it needs (`one` / `few` / `many`) already exist.
3. Register it in `DICTIONARIES` in `src/i18n/index.ts` (and in `dictionaries` if
   you want it in tests).
4. Run `npm run typecheck && npm test`. The parity tests compare key sets,
   placeholders and non-emptiness across every registered dictionary, so a
   forgotten `{percent}` or an empty string is caught, not shipped.

## Verification

`tests/i18n.test.ts` (17 tests; 116 in the suite) checks that:

- `en` and `ru` expose exactly the same key paths;
- no dictionary string is empty;
- `{placeholders}` match per key across languages — a Russian sentence that forgot
  `{limit}` fails the suite;
- every code the actions can send has a distinct Russian rendering;
- `errorText` localizes, fills placeholders, degrades to `errors.unknown` for junk
  input, and returns `null` when there is no code;
- `duplicateReasonText` handles a percent-bearing overlap reason and ignores a
  code it does not know;
- `plural` picks the Russian 2–4 form and keeps the 11–14 / 21 exceptions, and the
  Russian *few* strings genuinely differ from the *many* ones (a copy-paste would
  otherwise pass key parity and read wrong on every list of 2–4 leads);
- `eventMessageText` localizes a deduplicated sighting and leaves every other
  stored log line untouched.

Then the switcher was driven in the running console, and the following was
observed rather than assumed:

| Step | Observed |
| --- | --- |
| `GET /login` with no cookie | `lang="en"`, English copy, `aria-label="Language"` |
| Same URL with `lh_locale=ru` | `lang="ru"`, "Войти", "Пароль", switcher label "Язык" |
| Click **EN** on `/dashboard` | `document.cookie` → `lh_locale=en`, `lang="en"`, "Who needs your services right now", "score ≥ 80" |
| Click **RU** | cookie → `lh_locale=ru`, `lang="ru"`, "Кому прямо сейчас нужны ваши услуги", Cyrillic renders in the IBM Plex subset |
| Reload / navigate `/leads?minScore=80&temperature=HOT` | still Russian: "1 лид", "2 фильтра активно", 9 translated filters, "93/100" |
| `/leads/<id>?duplicate=overlapSameAuthor&percent=91` | "Уже в базе (тот же автор, совпадение текста 91%) — новая находка записана в этот лид…", dates as `15.10.2026, 20:01` |
| `/settings` | fully Russian, including saved-query controls |
| `/leads/new?error=<script>…` | degrades to "Что-то пошло не так. Смотрите журнал активности.", no code or URL text on screen |

One behaviour is still English by design and worth knowing: the activity trail of
the lead created before the codes refactor shows "Duplicate candidate ignored (same
author, 91% text overlap)", because that row's `metadata.reason` is prose, not a
code. New sightings render in Russian.
